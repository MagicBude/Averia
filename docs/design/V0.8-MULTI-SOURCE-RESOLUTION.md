## 1. 设计目标与原则

1. **字段级溯源**：每个正式字段值都能追到来源（哪个 source、哪个 observation）。
2. **显式归并，禁止模糊**：跨语言/跨源实体等同**只能**通过显式别名（`entity_aliases`）或人工 `resolution` 决策建立；字符串相似不触发自动合并。
3. **冲突不静默**：两个可靠来源对同一非空字段给出不同值 → 生成 `pending_review` 的 `field_resolutions`，**阻断**该字段 Apply，直到人工裁决。
4. **CSV 继续是唯一事实源**：新增三张表本身也是 CSV（正式数据集）；实体表里的“已解析值”用于展示/导出，解析表解释“怎么来的”。
5. **23 行无损**：新列（taxonomy 的 `name_en`）对既有行留空即合规；新数据集初始为空；`pnpm check` 在每阶段后必须仍全绿。

## 2. 新增三个正式数据集

### 2.1 `observations.csv`（字段级原始观察日志，append-only）

记录“某来源对某个实体的某字段观察到了什么值”。比 `source_records`（按实体）更细。

```text
id,entity_type,entity_id,source_name,source_record_id,field,observed_value,observed_language,observed_at,raw_hash,notes
```

- `id`：`obs_XXXXXX`（新增 ID 前缀）
- `entity_type`：actress|work|maker|label|series|genre|director
- `observed_language`：BCP47（`ja`/`en`/...）
- 永不覆盖，只追加；Provider raw 原文不受影响

示例（JavInfo 提供 Kana Momonogi）：
```text
obs_000001,actress,actress_000002,javinfo-fanza,work:ipzz00597,name_en,Kana Momonogi,en,2026-09-01T...,<hash>,
```

### 2.2 `field_resolutions.csv`（字段级裁决层）

记录“某实体的某字段最终采用哪个值、依据什么、胜出来源是谁”。

```text
id,entity_type,entity_id,field,resolved_value,resolution_method,winning_source_name,winning_source_record_id,confidence,conflicting_observation_ids,status,resolved_at,notes
```

- `id`：`res_XXXXXX`
- `resolution_method`：`auto_fill`（字段为空且单一来源）｜`rule_priority`（按字段优先级规则）｜`manual`（人工）｜`link`（通过别名/外部身份归并）
- `status`：`auto`（系统可安全写入）｜`pending_review`（需人工）｜`manual`（已裁决）
- `confidence`：`high`｜`medium`｜`low`
- `conflicting_observation_ids`：冲突时填入参与冲突的 `obs_*` 列表

示例（空字段由 JavInfo 英文源补全）：
```text
res_000001,actress,actress_000002,name_en,Kana Momonogi,auto_fill,javinfo-fanza,work:ipzz00597,high,,auto,2026-09-01T...,
```

冲突示例（两可靠源 release_date 不一致 → 阻断）：
```text
res_000002,work,work_00000X,release_date,,rule_priority,,,medium,"obs_000010,obs_000011",pending_review,,
```

### 2.3 `entity_aliases.csv`（跨源/跨语言别名与外部身份，显式）

覆盖**所有实体类型**的“另一个名字 / 另一个来源 ID”，供 matcher 精确匹配。与 `actress_aliases.csv` 并存但职责不同（见第 3 节）。

```text
id,entity_type,entity_id,alias,alias_type,language,source_name,source_record_id,notes,created_at
```

- `id`：`ea_XXXXXX`
- `entity_type`：actress|work|maker|label|series|genre|director
- `alias_type`：`romanized`｜`en`｜`ja`｜`cn`｜`kana`｜`external_id`（外部来源 ID，如 DMM actress id、JavInfo content id）
- `language`：BCP47

示例（把 JavInfo 英文 taxonomy 显式挂到既有日文实体）：
```text
ea_000001,maker,maker_000002,Idea Pocket,en,javinfo-fanza,work:ipzz00597,,
ea_000002,label,label_000002,Dish,en,javinfo-fanza,work:ipzz00597,,
ea_000003,genre,genre_000007,Slender,en,javinfo-fanza,work:ipzz00597,,
ea_000004,actress,actress_000002,Kana Momonogi,en,javinfo-fanza,work:ipzz00597,,
```

matcher 新增 `entity_aliases` 精确索引后，`Idea Pocket`/`Dish`/`Slender`/`Kana Momonogi` 都会**精确命中**既有 ID，不再新建重复实体。

## 3. 跨语言实体建模方案（回答“entity alias / external identity 如何建模”）

### 3.1 女优（已有能力，沿用）

- `actresses` 已有 `name_ja` / `name_en` / `kana` 三列。
- 罗马字/英文/中文等不同写法 → `actress_aliases.csv`（`alias_type` + `language`）。
- 归并 桃乃木かな ↔ Kana Momonogi：把 `Kana Momonogi` 写入 `actress_000002.name_en`（经 field_resolutions `auto_fill`，因其为空且 JavInfo 是可信英文源），或在 `actress_aliases` 加一条 `en` 别名。**二选一即可，推荐填 `name_en`**（实体表自解释，导出更干净）。

### 3.2 Taxonomy（maker/label/series/genre/director）—— 这是 Schema 改动的核心决策

当前它们只有 `name` + `name_ja`，无英文列，所以 JavInfo 的 `Idea Pocket`/`Dish`/`Slender` 无处安放、必然建重。两种取向（见第 7 节 Q1）：

- **方案 A（推荐）**：给 5 个 taxonomy schema 增加可选 `name_en` 列（向后兼容、对既有行留空即合规、校验通过、零数据迁移）。跨语言显示名直接进 `name_en`，由 `field_resolutions` 填充；外部来源 ID（DMM actress id、JavInfo content id）仍进 `entity_aliases`（`alias_type=external_id`）。
- **方案 B**：不增列，跨语言名全部走 `entity_aliases`（`alias_type=en`），实体表只保留日文 `name`/`name_ja`，英文仅作别名。改动更小但展示层需额外 join。

无论 A/B，`entity_aliases` 都承担**外部身份**（非“名字”的等价键）职责，且 matcher 匹配时把它当作**精确键**（与现有精确匹配同一级别，绝不模糊）。

### 3.3 防跨源错误合并的硬规则

matcher 匹配来源字符串时，只接受以下任一精确命中（新增 `entity_aliases` 索引与既有精确匹配并列）：

1. 同来源 `source_record_id` 映射；
2. 实体表 `primary_name`/`name_ja`/`name_en`/`kana`/`name` 规范化后相等；
3. `entity_aliases` 中已存在的显式别名/外部 ID 精确相等；
4. 作品标准化番号相等。

任何“看起来像但不相等” → 保持为独立候选 + 产生 `observation`/`field_resolutions(pending_review)`，**绝不直接合并**。

## 4. 任务书第 18 节问题逐条回答

**Q：observations 是否应重新成为正式数据集？**
是。`observations.csv` 作为 append-only 字段级观察日志，是 `source_records`（按实体）的细化，提供“字段级 provenance”。

**Q：field_resolutions 应如何设计？**
见 2.2。一个 `(entity_type, entity_id, field)` 一行，含 `resolved_value`/`resolution_method`/`winning_source`/`conflicting_observation_ids`/`status`/`confidence`。它是正式 CSV，可追踪、可人工裁决、可回滚。

**Q：entity alias / external identity 如何建模？**
见 2.3 + 第 3 节。新增通用 `entity_aliases.csv`（覆盖所有实体类型），`alias_type` 区分 `en`/`ja`/`cn`/`kana`/`external_id`；女优的人读别名继续用 `actress_aliases.csv`。matcher 把 `entity_aliases` 当精确键。

**Q：桃乃木かな ↔ Kana Momonogi？**
同一女优。`actress_000002` 已有 `name_ja=桃乃木かな`、`name_en` 空。JavInfo 给 `name_en=Kana Momonogi` → `field_resolutions` `auto_fill`（字段空、单一可信英文源）→ 写入 `name_en`，**不新建女优**。若 JavInfo 还给了冲突的 `name_ja`，则转 `pending_review`。

**Q：アイデアポケット ↔ Idea Pocket？**
同一厂商。`maker_000002` `name_ja=アイデアポケット`、无英文。方案 A 下填 `name_en=Idea Pocket`（field_resolutions）；方案 B 下在 `entity_aliases` 加 `ea(maker_000002, "Idea Pocket", en)`。matcher 之后精确命中 `maker_000002`，不建重。

**Q：ティッシュ ↔ Dish？**
同上，`label_000002` ↔ `Dish`。

**Q：スレンダー ↔ Slender？**
`genre_000007=スレンダー` 已由 DMM Rental 入库（见 0.1）。JavInfo `Slender` 通过 `name_en` 或 `entity_aliases` 挂到 `genre_000007`，不新建 genre。

**Q：Provider-specific taxonomy 是否保留原始值？**
保留。`raw.json` 永不删；`observations` 保留每个来源的原始观察字符串（如 JavInfo 的 `Slender` 与 DMM 的 `スレンダー` 各一条）；实体表只存一个归一化实体 + `name_ja`/`name_en`；原始 Provider 字符串可从 `observations` 回查。

**Q：如何防止跨源错误合并？**
见 3.3 硬规则 + AGENTS §4。只有显式 `source_record_id`、显式精确名、显式 `entity_aliases`、显式标准化番号四类精确键；相似即阻断并进入人工审核。

**Q：如何让人工审核进入流程？**
- `import:prepare` 产出 `stage.json`，除现有 `proposals` 外，新增 `observations` 与 `field_resolutions(pending_review)`；
- 新增 `pnpm resolution:report -- --batch <id>`：列出待审字段冲突及双方来源值；
- 新增 `pnpm resolution:decide -- --resolution <res_id> --value <选定值> [--source <胜出来源>]`：写 `status=manual` 并把选定值落到实体 CSV（经一次受控 Apply）；
- 新增 `pnpm resolve:link -- --alias "Kana Momonogi" --entity actress_000002 --type en`：用于“拒绝新建、改挂别名”的跨语言归并（即不建重、写 `entity_aliases` + `field_resolutions(link)`）；
- `import:apply` 在任何 `pending_review` 未处理时**阻断**（对应 AGENTS “冲突不可静默解决”）。

**Q：CSV Source of Truth 如何继续保持？**
`observations`/`field_resolutions`/`entity_aliases` 自身是正式 CSV；Apply 仍走“备份 → 写实体 CSV + 三张新表 → 全量校验失败回滚”的老机制；JSON/XLSX 由 CSV 重新生成。

**Q：现有 23 行如何无损兼容？**
- taxonomy 增 `name_en` 列为可选、既有行留空 → 校验通过、不改行；
- 三张新表初始为空 → 不影响既有 23 行；
- `nextIdFactory` 扩展识别 `obs_`/`res_`/`ea_` 前缀（小改动），ID 计数器扫描全库不受影响；
- 每阶段结束 `pnpm check` 必须仍 68+ 测试全绿、校验/质量无 error。

## 5. V0.8 数据流

```text
Provider（moodyz / dmm-rental / javinfo / javdatabase）
   │  raw.json + canonical.json + meta.json（保留原始，不丢）
   ▼
import:prepare
   ├─ 实体精确匹配（含新增 entity_aliases 索引）
   ├─ 追加确定新实体 / 关系 / 来源映射
   ├─ 对每个贡献字段写 observations（append）
   ├─ 空字段补全 → field_resolutions(auto_fill)
   └─ 冲突字段 → field_resolutions(pending_review)  【阻断该字段 Apply】
   ▼
import:report / resolution:report
   └─ 展示待追加、待审冲突、来源证据
   ▼
人工审核：resolution:decide / resolve:link
   ▼
import:apply
   └─ 校验无 pending_review → 备份 → 写实体 CSV + observations + field_resolutions + entity_aliases → 全量校验失败回滚
   ▼
data:export → JSON / XLSX（CSV 仍是 SoT）
```
